### Mini DevOps Stand: AlmaLinux 9 + Nginx + Systemd + Security

Комплексный проект настройки, защиты, траблшутинга и автоматизации серверной инфраструктуры на базе Enterprise Linux дистрибутива **AlmaLinux 9**.

---

## 📌 1. Информация о стенде
* **Дистрибутив:** AlmaLinux 9.x (Kernel 5.14, x86_64, RHEL-экосистема).
* **Гипервизор:** VMware Workstation / Player.
* **Конфигурация ВМ:** 2 vCPU, 2048 MB RAM, 20 GB NVMe Disk.
* **Сетевой режим:** VMware NAT Network (`192.168.239.0/24`), статический IP гостя: `192.168.239.129`.

---

## 🚀 2. Быстрый запуск стенда с нуля (Runbook)

Для полной автоматизации развертывания веб-сервера и окружения подготовлен bash-скрипт `scripts/provision.sh`.

# 1. Клонирование репозитория на сервер
git clone https://github.com/sheriilay/mini-devops-stand.git
cd mini-devops-stand

# 2. Запуск скрипта автоматической настройки
chmod +x scripts/provision.sh
sudo ./scripts/provision.sh
Скрипт автоматически установит Nginx, активирует службу, откроет HTTP-порт в firewalld, разместит векторный SVG-логотип и скорректирует контексты безопасности SELinux.

## ⚙️ 3. Архитектура и выполненные треки
Обязательная часть: Web-сервер и SSH
Что сделано:
Сгенерирована пара ключей ed25519 на хосте Windows; публичный ключ скопирован на ВМ в ~/.ssh/authorized_keys.
Развернут Nginx, стандартная страница заменена на кастомный HTML с логотипом logo.svg.
В firewalld разрешен сервис http (порт 80/tcp).
Исправлены метки SELinux командой restorecon -Rv /usr/share/nginx/html.
Почему выбран такой способ: Использована сеть VMware NAT с прямым доступом по IP 192.168.239.129. Это изолирует лабораторную сеть от домашнего роутера, но обеспечивает беспрепятственный доступ к сервисам с хоста.
Формула защиты:
Было сделано: размещение SVG и HTML в /usr/share/nginx/html с восстановлением контекстов httpd_sys_content_t через restorecon.
Потому что: SELinux в режиме Enforcing блокирует веб-серверу доступ к любым новым файлам без соответствующих меток (ошибка 403 Forbidden).
Проверено через: открытие http://192.168.239.129/ в браузере хоста.
Если сломается, смотреть: systemctl status nginx, логи /var/log/nginx/error.log и аудит SELinux audit2why < /var/log/audit/audit.log.

# Трек 1: «Файловая система и loop-диск»
Что сделано:
Создан файл-образ на 200MB через fallocate -l 200M /var/lib/images/artifacts.img.
Файл размечен в файловую систему ext4 через mkfs.ext4.
Смонтирован через loop-драйвер в каталог /srv/artifacts.
Запись добавлена в /etc/fstab с опцией loop,defaults 0 0.
Проведена перезагрузка ВМ (reboot), подтверждено сохранение данных файла release.txt.
Формула защиты:
Было сделано: добавление монтирования в /etc/fstab и проверка через mount -a.
Потому что: ручной mount сбрасывается при перезагрузке ОС. Использование UUID / блочных путей с обязательной проверкой mount -a гарантирует, что система не уйдет в Emergency Mode из-за синтаксической ошибки в fstab.
Проверено через: findmnt /srv/artifacts, df -h /srv/artifacts после ребута.
Если сломается, смотреть: журнал загрузки journalctl -xb и статус монтирования systemctl status srv-artifacts.mount.
# Трек 2: «Права доступа и пользователи»
Что сделано:
Создана группа devteam и пользователь devops_user без пароля.
Создан каталог /srv/shared с правами 2770 (drwxrws---) и владельцем root:devteam.
Настроен бит SGID (chmod 2770), обеспечивающий автоматическое наследование группы devteam для всех новых файлов.
Создан файл secret.txt с правами 600 (rw-------). Проверена блокировка чтения для пользователя devops_user.
Формула защиты:
Было сделано: установка специального бита SGID (2 в начале восьмеричной маски) на общий каталог.
Потому что: без SGID новые файлы создавались бы с первичной группой создателя, и коллеги по группе devteam не имели бы прав на совместную модификацию.
Проверено через: создание файла пользователем sudo -u devops_user touch ... и проверка владельца через ls -l.
Если сломается, смотреть: текущую маску umask, права родительских каталогов через namei -l /srv/shared/file.
# Трек 3: «Процессы, tmux и systemd»
Что сделано:
Продемонстрирован запуск процесса в tmux и показана ненадежность метода: при аварии процесса сервис не восстанавливается.
Оформлен промышленный systemd-юнит configs/myapp.service с директивами WorkingDirectory, User=devops_user, EnvironmentFile=/etc/myapp.env и Restart=on-failure.
Проведен краш-тест: процесс убит сигналом kill -9; systemd автоматически перезапустил процесс через 3 секунды с новым PID.
Запущена фоновая нагрузка sha1sum, изменен приоритет планировщика через renice -n 15 -p <PID> (зафиксировано в top, колонка NI = 15).
Формула защиты:
Было сделано: использование Restart=on-failure вместо Restart=always.
Потому что: on-failure перезапускает приложение только при сбоях (сигналы SIGKILL, SIGSEGV, ненулевые коды выхода), но позволяет штатно остановить сервис командой systemctl stop без его циклического самозапуска.
Проверено через: sudo kill -9 <PID> и просмотр systemctl status myapp.service (счетчик рестартов вырос, статус active).
Если сломается, смотреть: логи демона в journalctl -u myapp.service -e.
# Трек 4: «Сеть, SSH и безопасность»
Что сделано:
Харденинг SSH через drop-in конфиг /etc/ssh/sshd_config.d/99-hardening.conf: отключен парольный вход (PasswordAuthentication no) и вход под root (PermitRootLogin no).
Проброшен локальный зашифрованный туннель с хоста: ssh -L 8888:localhost:80 admin@192.168.239.129 -N (сайт открывается по http://localhost:8888).
Настроен firewalld: доступ к порту 8000 ограничен доверенной подсетью 192.168.239.0/24 через Rich Rules.
Продемонстрирована работа сырого TCP-сокета через nc -l -p 9999 и разъяснена разница между транспортным (L4) и прикладным (L7 HTTP) уровнями.
Формула защиты:
Было сделано: полный запрет парольной аутентификации в sshd.
Потому что: аутентификация по паролю уязвима для brute-force атак; криптографические ключи ed25519 невозможно скомпрометировать перебором.
Проверено через: ssh -o PubkeyAuthentication=no admin@192.168.239.129 (система возвращает Permission denied (publickey)).
Если сломается, смотреть: синтаксис sshd -t, логи авторизации journalctl -u sshd.
# Трек 5: «Мониторинг, инцидент и таймеры»
Что сделано:
Создан systemd.timer (uptime-logger.timer), каждые 5 минут логирующий аптайм в /tmp/uptime.log. Проверено расписание через systemctl list-timers.
Смоделирован инцидент: 100% заполнение диска /srv/artifacts дампом + 100% утилизация CPU процессом sha1sum.
Собрана полная системная диагностика (df -h, free -h, top, ss -s, dmesg, journalctl).
Ликвидированы последствия аварии, составлен Postmortem в файле report.md.

## 🔮 4. Что можно улучшить в следующий раз
Infrastructure as Code (IaC): Заменить ручную установку виртуальной машины на Vagrant (Vagrantfile) в связке с VirtualBox / Libvirt.
Конфигурационный менеджмент: Перенести выполнение задач треков в Ansible-плейбук для 100% идемпотентного развертывания на любом количестве серверов.
Безопасность sudoers: Настроить строгий аудит выполнения привилегированных команд через sudosh или аудит-демон auditd.
